# Перенос базы в eu-central-1

Почему: база стоит в `ap-southeast-2` (Сидней). Страница кабинета делает два похода
в базу подряд (проверить сессию, достать данные) и упирается в чистое ожидание сети.
Кода это не касается вообще.

Замер времени TCP-рукопожатия (один round-trip) из Казахстана до пулеров Supabase,
медиана пяти попыток:

```
Сидней (сейчас)   ap-southeast-2    953 мс
Лондон            eu-west-2         141 мс
Стокгольм         eu-north-1        147 мс
Франкфурт         eu-central-1      153 мс
Мумбаи            ap-south-1        243 мс
Сеул              ap-northeast-2    506 мс
Сингапур          ap-southeast-1    801 мс
```

Мумбаи вдвое ближе Франкфурта по карте и в полтора раза медленнее: трафик из
Казахстана уходит на запад, в европейские точки обмена, и до Индии идёт тем же
крюком. Лондон, Стокгольм и Франкфурт различаются в пределах дрожания сети.

Итог: страница станет ~300 мс вместо ~1.9 с.

Всё, что ниже, пишется в **PowerShell 5.1**: `&&` в нём — синтаксическая ошибка,
команды идут по одной.

## Чего менять нельзя

- **`CREDENTIALS_ENC_KEY` остаётся прежним.** Токены клиентов лежат в базе
  зашифрованными (AES-256-GCM, S4). С другим ключом они превратятся в мусор,
  и все подключённые аккаунты придётся заводить заново.
- **`SESSION_SECRET` остаётся прежним** — иначе CSRF-токены открытых вкладок
  перестанут сходиться и первая же отправка формы ответит 403.
- **`PUBLIC_BASE_URL` и адрес вебхука не меняются**: переезжает база, а не сервис.
  В настройках приложения Meta трогать нечего.
- **Сертификат `certs/supabase-prod-ca-2021.crt` остаётся прежним.** Это общий
  корневой сертификат Supabase (`CN=Supabase Root 2021 CA`, действует до 2031),
  а не сертификат проекта — он подойдёт проекту в любом регионе.

## Файл дампа — секрет

В нём лежат заявки клиентов (ПД), хэши сессий и зашифрованные токены. Держать его
**вне репозитория** — в командах ниже он пишется в `$HOME`, — и удалить, когда перенос
подтверждён. В `.gitignore` добавлена строка `/backup-*.dump` на случай промаха,
но полагаться на неё не нужно.

## Шаги

- [ ] **1. Новый проект.** Supabase → New project, регион **Central EU (Frankfurt)**,
      пароль базы сгенерировать и сохранить в менеджере паролей. Дождаться,
      пока проект поднимется.

- [ ] **2. Строки подключения.** Settings → Database → Connection string → вкладка
      **Session pooler** (порт 5432, тот же режим, что сейчас). Понадобятся обе:
      старая — из `.env`, новая — из нового проекта.

      Именно пулер, а не прямой хост `db.<ref>.supabase.co`: у новых проектов он
      отдаёт только IPv6 (записи A нет), и с площадки без IPv6 подключиться нечем.

      ```powershell
      $old = "postgresql://...ap-southeast-2...:5432/postgres"
      $new = "postgresql://...eu-central-1...:5432/postgres"
      ```

      Строки содержат пароли. Окно PowerShell после переноса закрыть, историю
      не сохранять.

- [ ] **3. Остановить сервис.** Дамп снимается с неподвижной базы: всё, что сервис
      запишет после дампа, потеряется. Вебхуки Instagram за это время Meta повторит
      сама, но не бесконечно — окно стоит держать в пределах десятка минут.

- [ ] **4. Дамп двух схем.** `public` — таблицы приложения, `drizzle` — журнал
      применённых миграций (без него `npm run migrate` попробует накатить всё заново).
      Служебные схемы Supabase (`auth`, `storage`, `extensions`) не трогаем: их
      новый проект создал себе сам.

      ```powershell
      pg_dump $old --schema=public --schema=drizzle --no-owner --no-privileges --format=custom --file="$HOME\backup-bot.dump"
      ```

- [ ] **5. Восстановление.** `--single-transaction` вместе с `ON_ERROR_STOP`: либо
      переносится всё, либо не переносится ничего и новая база остаётся пустой —
      разбираться с наполовину залитой базой хуже, чем начать заново.

      ```powershell
      pg_restore --dbname=$new --no-owner --no-privileges --single-transaction "$HOME\backup-bot.dump"
      ```

- [ ] **6. Сверить строки.** Число в обеих базах должно совпасть по каждой таблице:

      ```powershell
      $count = "select relname, n_live_tup from pg_stat_user_tables where schemaname='public' order by relname;"
      psql $old -c $count
      psql $new -c $count
      ```

      `n_live_tup` — оценка планировщика, а не точный счёт. Если числа разошлись
      на единицы, пересчитать точно по подозрительной таблице: `select count(*) from leads;`

- [ ] **7. Переключить `.env`.** `DATABASE_URL` на новую строку, хвост про TLS
      оставить дословно:

      ```
      DATABASE_URL=postgresql://...eu-central-1...:5432/postgres?sslmode=verify-full&sslrootcert=./certs/supabase-prod-ca-2021.crt
      ```

- [ ] **8. Проверить, что мигрировать нечего.** Журнал переехал вместе с данными,
      поэтому команда должна ничего не применить:

      ```powershell
      npm run migrate
      ```

      Если она собралась накатывать миграции с нуля — схема `drizzle` не доехала
      (шаг 4), и накатывать поверх готовых таблиц нельзя: вернуться к шагу 5.

- [ ] **9. Живая проверка захвата строк.** Тесты на PGlite `SKIP LOCKED` не проверяют:
      там одно соединение.

      ```powershell
      npm run db:check-locking
      ```

- [ ] **10. Запустить и замерить.** Открыть кабинет, засечь время загрузки страницы
      «Воронки» в DevTools → Network. Ожидание — около 300 мс вместо ~1.9 с.

- [ ] **11. Прибраться.** Удалить дамп: `Remove-Item "$HOME\backup-bot.dump"`.
      Старый проект в Сиднее **не удалять неделю** — это единственный путь назад,
      если что-то всплывёт. Удалить после недели спокойной работы.

## Если что-то пошло не так

Откат — это шаг 7 наоборот: вернуть в `.env` старую строку подключения и перезапустить.
Старый проект всё это время живой и содержит все данные на момент шага 4. Потерянными
окажутся только записи, сделанные в новой базе после переключения.
