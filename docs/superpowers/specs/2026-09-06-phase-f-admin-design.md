# Админка владельца — дизайн

Дата: 2026-09-06
Статус: утверждён владельцем в обсуждении.
Часть фазы F спеки `2026-08-27-saas-comment-to-dm-design.md`.

## 1. Задача

Владелец сервиса заводит клиентов, выдаёт им доступ в кабинет, подключает их
Instagram-аккаунты и отключает тех, кто перестал платить — через веб-интерфейс,
а не через `npm run seed` в консоли.

До этой фазы клиент появлялся только скриптом: владелец должен был иметь доступ
к машине с проектом. Продавать в таком виде нельзя.

## 2. Границы этой спеки

**Есть:**

- Список клиентов с их состоянием: подключён ли Instagram, сколько воронок, отключён ли.
- Заведение клиента по одному email.
- Выдача доступа ссылкой-приглашением: клиент сам ставит пароль, владелец его не знает.
- Подключение Instagram-аккаунта клиента: внешний id + токен, с перезаписью токена.
- Отключение и включение клиента обратно.
- Роль `owner` и function-level авторизация на всех маршрутах админки (S12).
- Скрипт создания первого владельца.

**Нет (сознательно):**

- **Нет OAuth.** Решение раздела 10 основной спеки остаётся в силе: OAuth требует Meta
  App Review, а это недели до первого клиента. Токен по-прежнему добывает владелец
  и вставляет в форму. Граница для OAuth уже существует — функция `connectAccount`
  принимает готовый токен и не спрашивает, откуда он; OAuth-callback позже вызовет
  ту же функцию, не затрагивая хранилище.
- **Нет удаления клиента.** Отключение обратимо, удаление — нет, а схема везде
  с `onDelete: 'cascade'`. Возвращается, когда появится запрос «удалите мои данные».
- **Нет входа владельца в кабинет клиента** (impersonation). Отдельная граница доверия,
  отдельная спека.
- **Нет остальной фазы F** — 24-часовое окно, троттлинг на клиента (S20), показ ошибок
  доставки, гигиена логов. Это независимые куски, они идут второй спекой.
- Нет смены email и нет самостоятельного восстановления пароля.

## 3. Модель данных

Две правки.

### `users` — колонка `disabled_at`

Nullable timestamp, а не boolean: в проекте флаги уже так и выражены (`sent_at`,
`processed_at`, `used_at`), и видно не только «отключён», но и когда.

### Новая таблица `invites`

| Колонка | Назначение |
|---|---|
| `id` | sha256 от токена приглашения |
| `user_id` | кому выдано, каскад от `users` |
| `expires_at` | срок жизни, из `INVITE_TTL_HOURS` |
| `used_at` | когда погашено; `NULL` — ещё действует |
| `created_at` | когда выдано |

`id` — это хэш, ровно как в `sessions`: у строки нет второго идентификатора, который
можно случайно отдать наружу, а дамп базы не даёт войти ни в один кабинет (S15).
Сам токен существует только в ссылке, которую владелец копирует, и нигде больше.

Одинаковые задачи выглядят одинаково: `invites` копирует `sessions` вплоть до способа
хранения, потому что обе решают «предъяви секрет — получи сессию».

### Форма запросов

Действительность приглашения проверяется в самом запросе, а не отдельным `if` после
выборки — тот же принцип, что держит S11:

```sql
WHERE id = ? AND used_at IS NULL AND expires_at > ?
```

Протухшее или уже использованное приглашение просто не находится.

## 4. Маршруты

### Плагин админки

Все маршруты регистрируются одним плагином с префиксом `/admin`. Внутри плагина —
единственный хук `onRequest`: нет сессии → редирект на `/login`; роль не `owner` → `403`.

Fastify инкапсулирует хуки: хук действует на маршруты своего плагина и только на них.
Новый маршрут внутри плагина защищён автоматически — забыть проверку физически нечего.
Это тот же приём, которым решён S11 (владелец вшит в `WHERE`), но для роли.

Отвергнутые варианты:

- вызов `requireOwner()` в каждом обработчике — защита держится на дисциплине,
  и тесты молчат, пока кто-то не напишет тест именно на новый маршрут;
- глобальный хук с проверкой `path.startsWith('/admin')` — защита на сравнении строк:
  `//admin`, `/admin/../admin`, регистр, каждый случай надо предусмотреть отдельно.

| Маршрут | Что делает |
|---|---|
| `GET /admin` | список клиентов: email, статус, подключён ли Instagram, число воронок |
| `POST /admin/clients` | завести клиента по email, показать ссылку приглашения |
| `POST /admin/clients/:id/invite` | перевыпустить ссылку |
| `POST /admin/clients/:id/toggle` | отключить или включить обратно |
| `POST /admin/clients/:id/accounts` | подключить Instagram: внешний id + токен |

В списке только строки с ролью `client`: владельцы сервиса собой не управляют.
Ссылка на `/admin` показывается в кабинете только владельцу — но это удобство,
а не защита: доступ закрыт хуком, а не отсутствием ссылки (S12).

### Публичные маршруты приглашения

Вне плагина: у гостя ещё нет сессии, и хук роли его не пропустил бы.

| Маршрут | Что делает |
|---|---|
| `GET /invite/:token` | форма установки пароля либо «ссылка недействительна» |
| `POST /invite/:token` | ставит пароль, гасит приглашение, входит в кабинет |

CSRF-токена на этой форме нет — по той же причине, что его нет на `/login`:
`csrfToken` выводится из сессии, а у гостя её нет. Защищают `SameSite=Lax`,
`form-action 'self'` в CSP и сам секрет в ссылке, которого атакующий не знает.

## 5. Потоки

### Заведение клиента

Владелец вводит email → создаётся `users(role='client')` → создаётся приглашение →
страница показывает ссылку. Ссылка видна один раз: в базе только хэш, восстановить
нечего, можно лишь перевыпустить.

Email в `users` уже под UNIQUE-индексом. Повторный email — это ошибка формы
с понятным текстом, а не падение обработчика: проверяем до вставки и всё равно
ловим нарушение ограничения, потому что между проверкой и вставкой есть щель.

Перевыпуск ссылки гасит все прежние приглашения этого клиента (`used_at = now`
на всех действующих). Иначе после «ссылка утекла, выпустите новую» старая
продолжала бы работать до конца своего срока.

### Приём приглашения

Гашение — одна атомарная операция, а не транзакция:

```sql
UPDATE invites SET used_at = ? WHERE id = ? AND used_at IS NULL AND expires_at > ?
```

Затронуто 0 строк — ссылка недействительна, дальше не идём. Двойной сабмит формы
не пройдёт дважды: гонку разруливает СУБД. Транзакция решала бы ту же задачу хуже —
проверка и запись разъезжаются на два шага, между которыми снова есть щель.

Дальше: argon2id, `deleteUserSessions` (S15), новая сессия, редирект в кабинет.

### Отключение клиента

Отключённость действует в трёх местах:

1. **Сессии** гаснут в момент отключения — `deleteUserSessions`, функция уже есть.
2. **Вход** не пускает. Текст ответа — тот же, что при неверном пароле (S13). Цена:
   отключённый клиент видит «Неверная почта или пароль» и недоумевает. Плата за то,
   чтобы перебором нельзя было отделить существующие аккаунты от несуществующих.
3. **Вебхук** отбрасывается: в `resolveAccountOwner` добавляется JOIN с условием
   `users.disabled_at IS NULL`. Отключённый клиент становится неотличим от неизвестного
   аккаунта, и срабатывает уже написанный S17.

Новое требование выражено через старое и не добавляет нового места для ошибки.

### Подключение Instagram-аккаунта

Внешний id проверяется как строка из цифр. Дальше три исхода:

| Состояние `(instagram, external_id)` | Что делаем |
|---|---|
| принадлежит **другому** клиенту | отказ |
| принадлежит **этому же** клиенту | обновляем токен |
| ничей | создаём запись |

Первая строка — не удобство, а требование: без неё клиент Б вписывает внешний id
аккаунта клиента А и перехватывает все его вебхуки. Это пробой S17 через админку.

Вторая строка тоже не удобство: токены Instagram живут 60 дней. Без перезаписи сервис
молча умирает через два месяца, и владельцу приходится править базу руками.

Токен наружу не возвращается никогда: в интерфейсе только «подключён / не подключён».

### Первый владелец

`npm run owner -- <email>` создаёт пользователя с ролью `owner` и печатает ссылку
приглашения. Пароль владелец ставит той же формой, что и клиенты: один путь установки
пароля на весь сервис, потому что второй путь — это второе место, где можно ошибиться.

## 6. Требования безопасности

| Требование | Как закрывается |
|---|---|
| **S12 (CRITICAL)** | `onRequest`-хук плагина админки |
| **S11 (CRITICAL)** | клиент не попадает в `/admin` вовсе; `:id` клиента читается только владельцем |
| **S13 (CRITICAL)** | argon2id, пароль 12–1024 символа, одинаковый ответ на любую неудачу входа |
| **S14 (HIGH)** | Zod-схемы `{email}`, `{password}`, `{externalAccountId, token}`; `role`, `user_id`, `disabled_at` из тела не читаются никогда |
| **S15 (HIGH)** | установка пароля гасит все сессии пользователя, новая выдаётся с нуля |
| **S17 (HIGH)** | отказ при попытке подключить чужой внешний id |
| **S19 (MEDIUM)** | троттлинг `/invite/:token` по адресу — иначе токен перебирается |
| **S21 (MEDIUM)** | email и все данные клиента выводятся тегом `html` |

### S9: токен приглашения в логе

Fastify логирует URL каждого запроса. `GET /invite/<токен>` уедет в лог целиком —
это секрет выше уровня `debug`, прямое нарушение S9.

Лечится сериализатором `req` в конфигурации логгера при создании Fastify: путь,
начинающийся с `/invite/`, пишется как `/invite/:token`. Требование в основной спеке
не описано, потому что до этой фазы секретов в путях не было.

## 7. Конфигурация

Две новые переменные, каждая — тремя синхронными правками (`EnvSchema`, `.env.example`,
`tests/config.test.ts`):

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `INVITE_TTL_HOURS` | срок жизни приглашения | 48 |
| `PUBLIC_BASE_URL` | основа ссылки приглашения | обязательная |

`PUBLIC_BASE_URL` обязательна и не выводится из заголовка `Host`: он приходит
от клиента, и ссылка приглашения увела бы токен на чужой домен.

## 9. Известные ограничения

- События, уже лежащие в `event_queue` и `outbox` на момент отключения клиента,
  будут доставлены. Окно — секунды (`WORKER_INTERVAL_MS`). Не чиним: цена фильтрации
  в очередях выше пользы.
- Ссылка приглашения попадает в историю браузера владельца. Смягчается сроком жизни
  и одноразовостью; `referrer-policy: same-origin` уже не даёт ей уйти на чужой домен.
- Отключённый клиент не понимает, почему не может войти. Осознанная плата за S13.
- Токены Instagram живут 60 дней. Перезапись токена реализована, но напоминания
  о скором истечении нет — это часть «запуска», второй спеки фазы F.
