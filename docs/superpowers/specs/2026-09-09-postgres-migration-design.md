# Перевод хранилища с SQLite на PostgreSQL — дизайн

Дата: 2026-09-09
Статус: проектирование

## 1. Зачем

Спека `2026-08-27-saas-comment-to-dm-design.md` (раздел «База — SQLite») откладывала
этот переход до момента, когда появится вторая копия процесса. Решение владельца —
делать переход сейчас, до того как этот момент наступит.

Выгода ровно одна и она конкретная: **вторая копия процесса**. Сегодня она невозможна.
`takePendingEvents` и `takeDueOutbox` просто читают неразобранные строки; два воркера
прочитали бы одни и те же и обработали событие дважды. У SQLite нет способа забрать
строку так, чтобы соседний процесс её пропустил. У Postgres есть — `FOR UPDATE SKIP
LOCKED`. Поэтому блокировка очередей входит в этот переход, а не откладывается: без неё
мы платим цену перехода и не получаем то, ради чего он делается.

Всё остальное (типы, индексы, размер базы) на нашем масштабе разницы не даёт и мотивом
не является.

## 2. Границы

**Меняется:** `src/storage/` целиком, `src/worker.ts`, вызовы запросов в `src/web/routes/`,
`scripts/`, `tests/storage/helpers.ts` и все тесты, работающие с БД.

**Не меняется:**

- `src/core/` — движок, матчер, троттлинг, типы. Он не знает про БД, и правило
  «`core/` без `drizzle`» продолжает проверять `tests/core/purity.test.ts`.
- `src/adapters/` — платформенные детали от хранилища не зависят.
- `src/storage/crypto.ts`, `src/storage/jsonMap.ts` — шифрование токенов (S4) и разбор
  `context_json` в `Map` (S6) работают со строками, а не с драйвером.
- `src/storage/files.ts` в части диска: байты как лежали в `FILES_DIR`, так и лежат.
  В БД остаётся только карточка файла. См. риск в разделе 9.
- Все требования S1–S22. Ни одно не ослабляется и не переформулируется.

## 3. Принятые решения

### 3.1 Драйвер — `node-postgres`

`drizzle-orm/node-postgres` поверх пула `pg`. Не `neon-http` и не `neon-serverless`:
они дают выигрыш в serverless-среде, где процесс живёт один запрос, а у нас процесс
долгоживущий и пул подключений ему полезен. Вендорный драйвер привязал бы нас к Neon
без причины; `pg` работает с Neon, Supabase, Railway и любым другим Postgres.

### 3.2 Окружение — только облако

Локального Postgres нет. Разработка ходит в облачную базу, прод — в свою.
Из этого следует раздел 3.3: тесты в облако ходить не могут.

### 3.3 Тесты — PGlite в памяти

`@electric-sql/pglite` + `drizzle-orm/pglite`. Это настоящий Postgres, собранный в WASM
и запущенный внутри процесса теста: тот же диалект, те же миграции, что в проде.

Почему не облачная тестовая база: сегодня `createTestDb()` даёт каждому из 21 файла
тестов свою чистую базу мгновенно и бесплатно, и на этом стоит обязательное правило
«два клиента в одной базе, клиент A не достаёт данные клиента B». Сетевая база
превращает прогон из секунд в десятки секунд, ломает параллельные прогоны vitest
и делает тесты незапускаемыми без интернета и без секретов в CI.

Цена решения названа честно: PGlite — отдельная зависимость (~30 МБ) и старт базы
занимает доли секунды вместо мгновенного `:memory:`. Отличия от настоящего сервера
у неё есть (нет репликации, часть расширений), но ни одной затронутой нами возможности
это не касается — включая `FOR UPDATE SKIP LOCKED`, который в тестах и проверяется.

### 3.4 Схема — минимальный диалект

`text`-идентификаторы остаются `text`, `context_json` остаётся `text`.
Меняются только те типы, у которых в Postgres нет прямого соответствия.

| Сейчас (`sqlite-core`) | Станет (`pg-core`) | Почему |
| --- | --- | --- |
| `sqliteTable` | `pgTable` | — |
| `text('id').primaryKey()` | без изменений | id генерируются `randomUUID()` в коде; тип `uuid` потребовал бы правок в тестах и ничего не даёт |
| `text('role', { enum: [...] })` | без изменений | `pg-core` поддерживает тот же `{ enum }`; `pgEnum` создал бы тип в БД и миграцию на каждое новое значение |
| `integer(..., { mode: 'timestamp' })` | `timestamp(..., { withTimezone: true, mode: 'date' })` | секунды epoch → `timestamptz`; на стороне TS остаётся `Date`, код не меняется |
| `integer('enabled', { mode: 'boolean' })` | `boolean('enabled')` | у Postgres есть настоящий boolean |
| `integer('position')`, `integer('size_bytes')`, `integer('attempts')` | без изменений | обычные целые |
| `index` / `uniqueIndex` | без изменений | имена индексов сохраняются один в один |

`uuid` вместо `text` и `jsonb` вместо `context_json` сознательно отложены. `jsonb` —
единственная часть, которая когда-нибудь окупится, но она тянет за собой `jsonMap.ts`,
то есть место, где вручную закрыт prototype pollution (S6). Трогать его заодно с
переездом — значит смешать два риска в одном диффе.

### 3.5 Дедупликация без ловли кода ошибки

Сейчас `markEventSeen` вставляет строку и ловит `error.code === 'SQLITE_CONSTRAINT_UNIQUE'`.
Это единственное место в `src/`, привязанное к конкретной СУБД по коду ошибки.
Замена SQLite-кода на SQLSTATE `23505` сохранила бы привязку, поэтому конструкция
меняется целиком:

```ts
const inserted = await db.insert(processedEvents)
  .values({ id: randomUUID(), userId, dedupeKey })
  .onConflictDoNothing()
  .returning({ id: processedEvents.id });
return inserted.length === 1;
```

Поведение то же: `true` — событие новое, `false` — уже видели. Прежнее свойство
сохраняется: любая другая ошибка по-прежнему летит наружу, а не превращается
в «уже виденное» — иначе событие тихо пропало бы навсегда.

## 4. Синхронный код становится асинхронным

`better-sqlite3` синхронный: `listAutomations(db, userId)` возвращает массив сразу.
Любой драйвер Postgres асинхронный. Это самая объёмная часть работы и она механическая:

- ~44 экспортируемых функции в `src/storage/queries/` (7 файлов) становятся `async`;
- `src/storage/files.ts` — функции, читающие и пишущие карточку файла;
- `src/worker.ts` — `runIntake` сейчас синхронная, станет `async`; `runDelivery` уже
  асинхронная. В `server.ts` оба вызова уже внутри `setInterval` с флагом `running`,
  поэтому сам цикл не переписывается — добавляется `await`;
- маршруты `src/web/routes/` — обработчики Fastify уже `async`, добавляются `await`;
- `scripts/seed.ts`, `scripts/create-owner.ts` — уже используют `await` для `hashPassword`,
  добавляются `await` на запросы.

Всего ~60 мест вызова `.all()` / `.get()` / `.run()`. Промежуточного «наполовину
зелёного» состояния не существует: сигнатуры меняются у всего слоя сразу, поэтому
ветка будет красной, пока не пройден шаг 3 из раздела 10.

Отдельно: `.all()` у drizzle-postgres не нужен — запрос сам является `Promise`.
`db.select()...limit(n)` возвращает массив после `await`, `.run()` заменяется на `await`
над `insert`/`update`.

## 5. Очереди и несколько процессов

`takePendingEvents` и `takeDueOutbox` — единственные две функции, которые обязаны
измениться по смыслу, а не механически. Обе получают `.for('update', { skipLocked: true })`:

```ts
export async function takePendingEvents(db: AppDb, limit = 20): Promise<EventRow[]> {
  return db.select().from(eventQueue)
    .where(isNull(eventQueue.processedAt))
    .orderBy(asc(eventQueue.createdAt))
    .limit(limit)
    .for('update', { skipLocked: true });
}
```

Блокировка живёт до конца транзакции, поэтому выборка и пометка строки обработанной
(`markEventProcessed`, `markOutboxSent`, `markOutboxFailed`) должны идти в одной
транзакции — иначе блокировка снимается сразу после `select`, и второй воркер заберёт
ту же строку. Транзакция открывается в `worker.ts`, вокруг обработки одной пачки:
шаг воркера остаётся вызываемым из теста, просто теперь он получает транзакцию.

Обе функции сохраняют осознанное исключение из S11 — без `userId` первым аргументом,
владелец уже записан в строке. Формулировка в `CLAUDE.md` не меняется.

## 6. Миграции и конфигурация

**Миграции пишутся с нуля.** `drizzle/0000_*.sql` и `0001_*.sql` — SQLite-синтаксис,
переносу не подлежат. Каталог `drizzle/` и `drizzle/meta/` очищаются, `drizzle.config.ts`
получает `dialect: 'postgresql'`, генерируется одна начальная миграция.

**Данные не переносятся.** В `data/bot.db` лежат три локальных аккаунта разработчика.
Они воссоздаются `npm run seed` и `npm run owner`. Писать одноразовый конвертер ради
трёх строк — работа, которая не окупится. Продовых данных не существует: сервис не
запущен.

**Автомиграция при старте снимается.** Сейчас `server.ts` вызывает `migrate()` на
каждом запуске. При нескольких копиях процесса это гонка: две копии применяют одну
миграцию одновременно. Миграции становятся отдельным шагом `npm run migrate` перед
запуском, а `server.ts` только открывает пул. В `CLAUDE.md` это правится вместе с кодом.

**`DATABASE_URL` меняет природу.** Был путь к файлу — станет строкой подключения
с паролем. В `config.ts` добавляется проверка префикса (`postgres://` или `postgresql://`):
опечатка вроде забытого `./data/bot.db` должна падать при старте с понятным именем
переменной, а не при первом запросе. Правило «новая переменная — три синхронные правки»
(`EnvSchema`, `.env.example`, `tests/config.test.ts`) действует и здесь, хотя переменная
не новая, а изменившаяся.

`openDb` теряет `mkdirSync` (каталога больше нет) и получает пул. Подпись остаётся
`openDb(url)`, тип `AppDb` остаётся единственной точкой, через которую слои видят БД.

## 7. Безопасность

Ни одно требование S1–S22 не меняет формулировку. Что требует внимания при правке:

- **S11.** Каждая функция в `queries/` сохраняет `userId` первым параметром и владельца
  в `WHERE`. Шесть задокументированных исключений остаются теми же шестью. Асинхронность
  создаёт новый способ ошибиться — потерянный `await` перед запросом вернёт `Promise`,
  который в `if` всегда истинный. Ловится строгим `tsconfig` и обязательным тестом
  «два клиента в одной базе» в каждой задаче, трогающей данные.
- **S10.** `DATABASE_URL` теперь секрет. `config.ts` печатает только имена переменных —
  правило уже написано и его достаточно, но при добавлении проверки префикса нельзя
  подставлять значение в текст ошибки.
- **S4, S9.** Объект ошибки драйвера `pg` содержит фрагмент SQL и параметры запроса,
  то есть при неудачной вставке — тело сообщения или зашифрованный токен. Правило
  «не логировать объект ошибки целиком» становится строже по последствиям, чем было
  с `better-sqlite3`. Существующий `tests/security/logging.test.ts` расширяется.
- **Транспорт.** Соединение с облачной базой обязано идти по TLS (`sslmode=require`
  в строке подключения). Отдельной переменной для этого не заводим: режим — часть URL.

## 8. Тестирование

`tests/storage/helpers.ts` — единственное место, которое знает про PGlite:

```ts
export async function createTestDb(): Promise<AppDb> {
  const client = new PGlite();
  const db = drizzle(client);
  await migrate(db, { migrationsFolder: './drizzle' });
  return db;
}
```

Функция становится асинхронной, поэтому каждый тест с БД получает `await createTestDb()`.
Это единственная правка, которая касается всех 21 файла одинаково.

Уровни тестов и их назначение не меняются. Добавляется один новый тест:
**две параллельные выборки из `event_queue` не возвращают одну строку дважды** —
это проверка `SKIP LOCKED`, то есть проверка того самого свойства, ради которого
делается переход. Без него раздел 1 не выполнен.

## 9. Риски и что осталось за границами

- **Файлы остаются на локальном диске.** `FILES_DIR` — каталог процесса. Пока копия
  процесса одна, это работает. Вторая копия файл, загруженный первой, не увидит:
  клиент загрузит PDF через один процесс, а отправит его воркер в другом и получит
  «файла нет». То есть переход на Postgres снимает первое препятствие к нескольким
  процессам, но не последнее. Общее хранилище файлов — отдельная задача, в эту спеку
  не входит и обязана быть решена до того, как копий станет больше одной.
- **Троттлинг живёт в памяти процесса.** `ReplyThrottle` — три экземпляра в `server.ts`
  (ответы бота S8, лимит на клиента S20, попытки входа S22). При двух процессах каждый
  считает свою половину, и фактические лимиты удваиваются. Для S8 и S20 это ослабление
  защиты от блокировки платформой, для S22 — ослабление защиты от подбора пароля.
  Тоже за границами этой спеки и тоже обязано быть решено до второй копии.
- **PGlite ≠ управляемый Postgres.** Тесты зелёные на PGlite не гарантируют поведение
  под нагрузкой в облаке. Смягчение: диалект и миграции те же, а расхождения
  ожидаются в областях, которых мы не касаемся.
- **Ветка красная в середине перехода.** Это следствие смены сигнатур, а не
  неаккуратности. Порядок работ ниже выбран так, чтобы красный участок был коротким
  и предсказуемым.

## 10. Порядок работ

1. Зависимости: `pg`, `@types/pg`, `@electric-sql/pglite`. Удалить `better-sqlite3`
   и `@types/better-sqlite3`. Проверить `npm audit`.
2. `schema.ts` на `pg-core` по таблице из 3.4. Очистить `drizzle/`, поставить
   `dialect: 'postgresql'` в `drizzle.config.ts`, сгенерировать начальную миграцию.
3. `db.ts` на пул `pg`; `tests/storage/helpers.ts` на PGlite; `config.ts` — проверка
   префикса `DATABASE_URL`; `.env.example` и `tests/config.test.ts`.
4. `queries/` по одному файлу за задачу, в порядке `users` → `sessions` → `invites` →
   `accounts` → `automations` → `leads` → `runtime`. Тесты соответствующего файла
   зеленеют в той же задаче. Каждая задача заканчивается коммитом.
5. `files.ts` — карточка файла асинхронно, работа с диском без изменений.
6. `takePendingEvents` и `takeDueOutbox` — `SKIP LOCKED` и транзакция в `worker.ts`;
   новый тест из раздела 8.
7. `worker.ts`, маршруты, `scripts/` — дотянуть `await`. Снять `migrate()` со старта
   `server.ts`.
8. `tests/security/logging.test.ts` — ошибка драйвера `pg` не утекает в лог.
9. `CLAUDE.md`: команды (`npm run migrate` перед запуском), слой `storage/`,
   природа `DATABASE_URL`, замена `:memory:` на PGlite в разделе про тесты.
10. Контрольная точка фазы: `npm run check`, `npm audit`, `npx drizzle-kit check`.
