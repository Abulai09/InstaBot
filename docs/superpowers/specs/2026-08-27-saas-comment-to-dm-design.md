# SaaS «комментарий → директ» — дизайн

Дата: 2026-08-27
Статус: утверждён владельцем в обсуждении. Заменяет `2026-08-26-chatbot-design.md`.

## 1. Задача

Сервис, в котором владелец Instagram-аккаунта через веб-интерфейс настраивает автоответы
на комментарии и цепочки сообщений в директ. Человек оставляет комментарий с ключевым
словом — бот отвечает в комментариях и одновременно пишет в директ заранее заданную
цепочку сообщений, включая файл (PDF-чеклист, прайс, гайд).

Продукт многопользовательский: у каждого клиента сервиса свой кабинет, свои
автоматизации, свои файлы и свои заявки. Без AI — поведение задаёт детерминированный
конечный автомат.

## 2. Границы v1

**Есть:**

- Вход по логину и паролю. Аккаунты клиентов заводит владелец сервиса.
- Кабинет: список автоматизаций, включение и выключение каждой.
- Конструктор в виде формы: слово-триггер → ответ в комментарий → цепочка сообщений
  в директ → файл → кнопки.
- Загрузка файлов (PDF, изображения) и отправка их в директ.
- Таблица собранных заявок с выгрузкой в CSV.
- Админка владельца: завести клиента, подключить его Instagram, выдать доступ.
- Instagram: комментарии и директ, полный сценарий.

**Нет (сознательно):**

- Нет самостоятельной регистрации и нет OAuth-подключения аккаунтов. Клиентов заводит
  владелец вручную. Потолок такой схемы — порядка 20 клиентов; этого достаточно,
  чтобы проверить спрос до подачи на Meta App Review.
- Нет TikTok в v1 — отдельная фаза после запуска Instagram.
- Нет приёма оплаты внутри сервиса.
- Нет визуального редактора со стрелками — только форма.
- Нет ветвлений в воронке: цепочка линейная. Кнопки есть, но ведут по той же цепочке.
- Нет AI и LLM.

## 3. Ограничения платформ (проверено 2026-08-27)

| Платформа | Приём событий | Что доступно |
|---|---|---|
| Instagram | webhook (push) | DM + комментарии; окно ответа 24 часа |
| TikTok | только polling | ответ на комментарии Business-аккаунта; DM API отсутствует |

**Файлы в директ Instagram.** Поддерживаются вложения типа `file` (PDF до 25 МБ),
`image` (png, jpeg, до 8 МБ), `video` и `audio` (до 25 МБ).

Два следствия для архитектуры:

1. **Одно сообщение содержит либо текст, либо вложение, но не оба сразу.** «Приветствие
   плюс чеклист» — это два последовательных сообщения. Движок уже возвращает список
   действий, поэтому в ядре ничего менять не нужно.
2. **Вложение отправляется либо по публичному URL, либо по `attachment_id`.** Выбран
   `attachment_id`: файл выгружается в Meta один раз, дальше все отправки идут по
   идентификатору. Лид-магнит уходит тысячам людей — иначе Meta выкачивала бы файл
   с нашего сервера при каждой отправке, и файлы пришлось бы держать доступными
   по публичным ссылкам, то есть без авторизации.

Источник: `developers.facebook.com/docs/instagram-platform/instagram-api-with-instagram-login/messaging-api/`

**TikTok** (перенесено из предыдущей спеки, актуально): вебхука на новый комментарий
не существует — только опрос. Общего DM API нет: Business Messaging доступен лишь
через партнёрскую программу, Shop Customer Service API — только по заказам в Shop.
Для мультитенантного сервиса TikTok потребует отдельного согласования приложения;
это проверяется в фазе G, а не принимается на веру.

## 4. Архитектура

Слои, зависимости направлены только внутрь — к `core/`:

```
core/       types, scenario, matcher, engine, throttle    чистая логика, без сети и БД
storage/    schema, db, queries, crypto, files            SQLite через Drizzle
adapters/   instagram/ (push), tiktok/ (pull, фаза G)     платформенные детали
web/        auth, routes/, views/                         кабинет и админка
```

`files` — модуль внутри `storage/`, а не отдельный слой: он хранит и отдаёт байты,
это разновидность доступа к данным.

### Ядро не меняется

Универсальность держится на двух типах из `core/types.ts`: всё входящее приводится
к `IncomingEvent`, всё исходящее — к `OutgoingAction`. Движок остаётся чистой функцией
`step(scenarios, state, event) -> { state, actions }`.

Конструктор в браузере сохраняет строки в `automations` и `automation_steps`; перед
исполнением из этих строк собирается объект `Scenario` — тот же тип, который раньше
приходил из YAML:

```
форма в браузере -> строки в БД -> Scenario -> step() -> OutgoingAction[]
```

Поэтому `engine.ts`, `matcher.ts`, `throttle.ts` в этом продукте не меняются.

### Судьба YAML

Сценарии переезжают в БД, `loadScenarios(dir)` в продукте больше не используется.
`ScenarioSchema` (Zod) остаётся и становится важнее: раньше он проверял файл от
владельца, теперь — данные из формы, присланные браузером. `parseScenario` сохраняется
для импорта и экспорта воронок (шаблоны, перенос между аккаунтами).

### Определение владельца входящего события

Meta шлёт вебхуки всех клиентов на один наш адрес. Владелец определяется по
идентификатору Instagram-аккаунта получателя:

```
вебхук -> проверка подписи (S1)
       -> id аккаунта получателя -> поиск в platform_accounts -> userId
       -> аккаунт не найден -> событие отбрасывается (S17)
       -> event_queue (с userId) -> 200 OK
```

### Поток данных

```
Instagram: Meta -> POST /webhooks/instagram -> подпись -> владелец -> event_queue -> 200 OK
worker:    event_queue -> воронки этого клиента -> состояние диалога -> step()
                       -> сохранение состояния -> outbox -> adapter.execute()
                       -> собранные ответы -> leads
web:       браузер -> сессия -> userId -> запросы только с этим userId
```

Веб-интерфейс и бот работают в одном процессе: общий деплой, общая база. Разделение
на два процесса — когда этого потребует нагрузка, не раньше.

## 5. Модель данных

У каждой строки есть владелец. Почти каждая таблица содержит `user_id`, и каждый
запрос фильтрует по нему.

| Таблица | Назначение |
|---|---|
| `users` | клиенты сервиса: email, хэш пароля, роль (`client` / `owner`) |
| `platform_accounts` | подключённый аккаунт: `user_id`, платформа, внешний id, зашифрованный токен |
| `automations` | воронка: `user_id`, название, триггер (тип + значение), включена ли |
| `automation_steps` | шаги: `automation_id`, порядок, текст, `file_id`, имя переменной, кнопки |
| `files` | загруженное: `user_id`, оригинальное имя, путь на диске, mime, размер, `attachment_id` |
| `leads` | заявки: `user_id`, `automation_id`, контакт, собранные ответы, дата |
| `conversations` | состояние диалогов: `user_id`, платформа, тред, `step_id`, `context_json` |
| `event_queue` | входящие события: `user_id`, платформа, тело |
| `processed_events` | дедупликация: UNIQUE по `dedupe_key` |
| `outbox` | исходящие действия: `user_id`, попытки, время следующей попытки |
| `sessions` | сессии входа |

`conversations` — это `ConversationState` из `core/types.ts` с добавленным владельцем.

**База — SQLite.** Достаточно для десятков клиентов и одного процесса. Пересматривать,
когда появится вторая копия процесса или записи начнут блокировать друг друга; переход
на Postgres затрагивает только `storage/`.

### Форма функций доступа к данным

Все запросы к данным клиента принимают `userId` первым аргументом:

```ts
listAutomations(userId)
getAutomation(userId, automationId)
```

Функции вида `getAutomation(id)` без владельца в этом слое не существует. Инвариант
изоляции держится формой сигнатур, а не внимательностью вызывающего кода.

Слой запросов появляется там, где он держит этот инвариант, а не как обёртка над
каждой таблицей по шаблону.

## 6. Обработка ошибок

- HTTP-обработчик вебхука отвечает быстро: проверка подписи, запись в очередь, `200 OK`.
  Meta отключает медленные приложения.
- Надёжность лежит в БД, а не в Redis: `processed_events` (обе платформы доставляют
  at-least-once), `event_queue`, `outbox` с `attempts` и `next_attempt_at`
  (экспоненциальная задержка).
- Осмысленный 4xx от платформы — не повторять, пометить, показать клиенту в кабинете.
- Выход за 24-часовое окно Instagram — не сетевая ошибка, а бизнес-ситуация: решает
  сценарий.
- Ошибки не глотаются молча и не возвращаются наружу со стек-трейсом: клиенту —
  сообщение без внутренних деталей, подробности — в лог.

## 7. Требования безопасности

Требования, а не рекомендации. Тесты на них помечаются номером `S…` в названии.

### Границы доверия

| Граница | Что через неё проходит |
|---|---|
| Meta → наш вебхук | тела событий от внешней сети; подлинность только по подписи |
| браузер клиента → веб | формы, загружаемые файлы, идентификаторы ресурсов |
| клиент A → данные клиента B | всё, что адресуется по id: воронки, файлы, заявки, диалоги |
| клиент → админка владельца | маршруты заведения клиентов и подключения аккаунтов |
| наша БД → Meta API | тексты и файлы, которые уходят наружу от имени клиента |

### Перенесено без изменений

- **S1 (CRITICAL).** `X-Hub-Signature-256` — HMAC-SHA256 от сырых байт тела на App Secret,
  сравнение только `timingSafeEqual` с предварительной проверкой длины, несовпадение →
  `403` без тела. Fastify парсит JSON по умолчанию, поэтому сырое тело нужно сохранить
  до парсинга: `JSON.stringify(req.body)` не равен исходным байтам.
- **S2 (CRITICAL).** `hub.verify_token` в GET-хендшейке сравнивается constant-time.
- **S3 (HIGH).** Эхо-вебхуки (`message.is_echo`) отбрасываются до очереди — иначе
  бесконечная петля самоответов.
- **S4 (HIGH).** Токены платформ хранятся в `platform_accounts` зашифрованными
  AES-256-GCM на ключе `CREDENTIALS_ENC_KEY` из окружения.
- **S5 (HIGH).** YAML грузится только `CORE_SCHEMA`, результат валидируется Zod.
- **S6 (MEDIUM).** Контекст диалога — `Map<string, string>`, не объектный литерал
  (prototype pollution через `__proto__`).
- **S7 (MEDIUM).** Регулярные выражения в триггерах запрещены: только `exact`,
  `contains`, `starts_with`. Текст обрезается по длине до матчинга.
- **S8 (MEDIUM).** Троттлинг на контакт: не более N ответов в минуту.
- **S9, S10.** Секреты и ПД не логируются выше уровня `debug`, в том числе через
  «залогировать весь объект ошибки»; ошибка валидации окружения печатает только имена
  переменных, не значения.

### Новое: многопользовательность и веб-интерфейс

- **S11 (CRITICAL). Object-level авторизация (IDOR).** Клиент не может получить доступ
  к чужим воронкам, файлам, заявкам, диалогам и подключённым аккаунтам — ни чтением,
  ни изменением, ни удалением. Проверка принадлежности выполняется в том же запросе,
  что и выборка (`WHERE id = ? AND user_id = ?`), а не отдельным условием после неё.
  Отдельный тест на каждый ресурс и каждый метод.
- **S12 (CRITICAL). Function-level авторизация.** Маршруты админки доступны только
  роли `owner`. Проверка роли — на сервере, на каждом таком маршруте; отсутствие ссылки
  в интерфейсе не является защитой. Тест: клиент с ролью `client` получает `403`
  на каждом маршруте админки.
- **S13 (CRITICAL). Пароли.** Хранятся только как хэш (argon2id, при недоступности —
  bcrypt с cost не ниже 12). Никогда открытым текстом и никогда обратимым шифрованием.
  Ответ при неверном логине и при неверном пароле одинаков — иначе перебором собирается
  список существующих аккаунтов.
- **S14 (HIGH). Mass assignment.** `user_id`, роль, `attachment_id` и любые
  идентификаторы владения **никогда** не читаются из тела запроса. Владелец берётся
  только из сессии. Схема Zod для каждой формы описывает ровно разрешённые поля,
  лишние отбрасываются.
- **S15 (HIGH). Сессии и CSRF.** Cookie сессии — `HttpOnly`, `Secure`, `SameSite=Lax`.
  Идентификатор сессии перевыпускается при входе (защита от фиксации сессии) и
  инвалидируется при смене пароля и при выходе. Каждая изменяющая форма несёт
  CSRF-токен, привязанный к сессии.
- **S16 (HIGH). Загрузка файлов.** Проверяются размер (не выше лимитов Meta), заявленный
  MIME **и** фактическая сигнатура файла, а также расширение по белому списку.
  Файл сохраняется под сгенерированным именем вне веб-корня; присланное имя
  используется только для отображения и экранируется при выводе.
- **S17 (HIGH). Изоляция вебхуков.** Событие для неизвестного `platform_account`
  отбрасывается, а не обрабатывается «по умолчанию».
- **S18 (HIGH). Path traversal при отдаче файла.** Файл отдаётся только по записи
  в таблице `files`, найденной с фильтром по `user_id`; путь на диске никогда
  не собирается из данных запроса. Заголовок `Content-Disposition: attachment`
  и `X-Content-Type-Options: nosniff`.
- **S19 (MEDIUM). Троттлинг входа.** Ограничение числа неудачных попыток пароля
  на аккаунт и на IP.
- **S20 (MEDIUM). Троттлинг на клиента.** Помимо лимита на контакт (S8) действует
  лимит на клиента сервиса, чтобы один клиент не выжег общие лимиты API.
- **S21 (MEDIUM). XSS.** Тексты воронок, имена файлов и данные заявок выводятся только
  через экранирование шаблонизатора. Дополнительный рубеж — `Content-Security-Policy`
  без `unsafe-inline`. Проверяется тестом: воронка с именем `<script>` не выполняется
  на странице списка.
- **S22 (LOW). Заголовки.** `X-Frame-Options: DENY` (или `frame-ancestors 'none'`),
  `X-Content-Type-Options: nosniff`, HSTS в проде.

### Проверка зависимостей

`npm audit` входит в контрольную точку фазы наравне с тестами и typecheck. Новая
зависимость добавляется осознанно: смотрим, что она тянет транзитивно и живой ли проект.

## 8. Тестирование

`tests/` зеркалит `src/`. Пять уровней:

- **unit** — движок, матчер, троттлинг: таблица «событие → ожидаемые действия», без моков.
- **contract** — адаптеры против сохранённых реальных тел вебхуков в `fixtures/`.
- **security** — S1, S2, S3 и S11–S22 отдельными тестами с номером в названии.
- **integration** — фейковый адаптер и БД `:memory:`, прогон воронки целиком.
- **web** — маршруты кабинета через `fastify.inject()`, без реального HTTP.

Обязательный тест в каждой фазе, затрагивающей данные: **два клиента в одной базе**.
Клиент A и клиент B, у каждого воронки, файлы и заявки; A не достаёт ничего из B
ни одним маршрутом и ни одним методом.

## 9. Фазы

Порядок задан риском: сначала то, что может не получиться. Живой бот идёт раньше
кабинета; на этом этапе воронки засеваются скриптом.

| Фаза | Содержание | Результат |
|---|---|---|
| A | Хранилище: схема с `user_id`, шифрование токенов, слой запросов, тесты IDOR | чужое не достать |
| B | Instagram сквозняком: подпись → вебхук → воркер → ответ текстом | бот отвечает живому человеку |
| C | Файлы: загрузка, выгрузка в Meta, PDF в директ | главный сценарий работает целиком |
| D | Вход и кабинет: сессии, список воронок, заявки, CSV | клиент видит свои заявки |
| E | Конструктор: форма создания и правки воронки | клиент настраивает сам |
| F | Админка и запуск: заведение клиентов, 24-часовое окно, гигиена логов | можно продавать |

Фазы A–F составляют v1. После них:

| Фаза | Содержание | Результат |
|---|---|---|
| G | TikTok: адаптер на polling | вторая сеть |

Готово к моменту написания спеки: конфигурация (`src/config.ts`), типы ядра,
загрузка и валидация сценариев, матчер триггеров, движок, троттлинг — с тестами.
Эта работа переносится в новый план как выполненная.

## 10. Ключевые решения и их цена

**Подключение аккаунтов вручную вместо OAuth.** OAuth требует Meta App Review:
юрлицо, верификация бизнеса, проверка готового продукта — недели ожидания до первого
клиента. Ручное подключение позволяет проверить спрос сразу, ценой потолка примерно
в 20 клиентов. OAuth добавляется позже как отдельный модуль «откуда взялся токен»,
не затрагивая остальной продукт.

**Серверный рендеринг вместо SPA.** Для формы-анкеты SPA не даёт выигрыша, но добавляет
вторую сборку, второй деплой и дублирование типов между фронтом и бэком. Граница
закладывается так, чтобы позже можно было отдать JSON и подключить React, не переписывая
бэкенд.

**Заявки в таблице вместо уведомлений оператору.** В однопользовательской версии заявка
уходила уведомлением. С появлением кабинета у каждого клиента есть место, где заявки
видны; это снимает вопрос «куда слать уведомление» и настройку канала для каждого
клиента. Уведомления возвращаются позже как надстройка.

**Один процесс на бота и интерфейс.** Общий деплой и общая база проще в эксплуатации.
Цена — общий отказ: падение веб-части останавливает и обработку событий. Пересматривать
при появлении нагрузки или требований к доступности.

**`attachment_id` вместо публичных ссылок на файлы.** Меньше трафика и, главное,
файлы клиентов не лежат в открытом доступе.

**SQLite.** См. раздел 5.

## 11. Открытое решение владельца

`core/matcher.ts` — функция `matches(trigger, userText)` реализована владельцем и
остаётся его зоной ответственности: от строгости сравнения зависит доля клиентов,
которых бот проигнорирует. В SaaS-версии цена ошибки выше — правило действует
для всех клиентов сервиса сразу.
