## Что это за проект

Мультитенантный сервис: владелец Instagram-аккаунта через веб-интерфейс настраивает
автоответы на комментарии и цепочки сообщений в директ. Человек пишет комментарий
с ключевым словом — бот отвечает в комментариях и одновременно шлёт в директ
заданную цепочку сообщений с файлом (PDF-чеклист, прайс, гайд).

У каждого клиента сервиса свой кабинет, свои автоматизации, файлы и заявки.
Без AI — поведение задаёт детерминированный конечный автомат.

Источники истины:

- `docs/superpowers/specs/2026-08-27-saas-comment-to-dm-design.md` — дизайн, границы v1,
  требования безопасности S1–S22, фазы A–G.
- Фазы A–G выполнены целиком, планы лежат в `docs/superpowers/plans/` с датами
  2026-08-27, 2026-08-28, 2026-09-01, 2026-09-02 и 2026-09-09.
- Фаза F разделена надвое, у каждой половины своя спека:
  `2026-09-06-phase-f-admin-design.md` — админка владельца (клиенты, приглашения
  по ссылке, подключение аккаунта, отключение клиента), роль `owner`, таблица
  `invites`, колонка `users.disabled_at`; `2026-09-09-phase-f-runtime-design.md` —
  24-часовое окно, троттлинг на клиента (S20), показ ошибок доставки, гигиена логов.
- `docs/superpowers/specs/2026-09-09-phase-g-tiktok-design.md` — фаза G: TikTok
  на polling. Код написан и покрыт тестами против сохранённых ответов, но против
  живого TikTok Business API ещё не проверялся. `TIKTOK_CLIENT_KEY` и
  `TIKTOK_CLIENT_SECRET` объявлены в конфиге и пока нигде не используются: токен,
  как и у Instagram, вводится руками в админке.
- `docs/superpowers/specs/2026-09-09-postgres-migration-design.md` — перевод хранилища
  с SQLite на PostgreSQL: захват строк очередей (`FOR UPDATE SKIP LOCKED`), лизинг
  outbox, TLS до облачной базы. Плана в `docs/superpowers/plans/` нет, работа шла
  по спеке; ветка `postgres-migration`.
- `docs/superpowers/plans/2026-09-11-postgres-region-move.md` — единственная незакрытая
  работа: перенос базы из `ap-southeast-2` в `eu-central-1`. Кода не касается вообще,
  это 11 ручных шагов в Supabase и `.env`, ни один не отмечен. Причина — рукопожатие
  до Сиднея (953 мс медиана), из-за него страница кабинета стоит ~1.9 с. При переносе
  нельзя менять `CREDENTIALS_ENC_KEY` (токены клиентов станут мусором) и
  `SESSION_SECRET` (CSRF открытых вкладок перестанет сходиться).

Планы пишутся **на одну фазу вперёд**: план, написанный до появления кода предыдущей
фазы, расходится с реальными сигнатурами, а расходящемуся плану верят.

`docs/superpowers/specs/2026-08-26-chatbot-design.md` и
`docs/superpowers/plans/2026-08-26-multiplatform-chatbot.md` — предыдущая версия продукта
(бот для одного бизнеса). Оставлены как история; задачи 8, 9, 10, 12 оттуда
переиспользуются в фазе B почти без изменений.

Текущий прогресс определяется чекбоксами `- [ ]` в плане фазы и `git log --oneline`,
а не записью в этом файле.

## Команды

```bash
npm test                                   # vitest run — весь набор
npx vitest run tests/core/                 # один каталог
npx vitest run tests/storage/crypto.test.ts # один файл
npx vitest run -t "S11"                    # тесты по номеру требования в названии
npm run typecheck                          # tsc --noEmit, покрывает src/, tests/ и scripts/
npm run check                              # тесты + typecheck одной командой
npm run migrate                            # накатить миграции — обязательный шаг перед запуском
npx drizzle-kit generate                   # новая миграция после правки src/storage/schema.ts
npm audit                                  # входит в контрольную точку фазы (ожидается 0)
npm run dev                                # сервер и воркер в одном процессе, с перезапуском
npm start                                  # то же самое без watch
npm run seed -- <email> <ig-id> <token> <пароль> [файл.pdf]   # клиент, воронка, вход
npm run owner -- <email>                   # первый владелец сервиса + одноразовая ссылка
TIKTOK_TEST_TOKEN=<токен> npm run tiktok:check -- <business_id> [--show-text]
npm run db:check-locking                   # живая проверка SKIP LOCKED против облачной базы
npm ci --omit=dev                          # установка на сервере; `--omit=optional` добавлять нельзя
```

Миграции сами не применяются: `server.ts` только открывает пул, `npm run migrate` —
отдельный шаг **перед** запуском. Автомиграция при старте была бы гонкой, как только
копий процесса станет больше одной.

`.env` подхватывают все команды, но по-разному: `dev`, `start`, `seed`, `owner`,
`tiktok:check`, `db:check-locking` — флагом Node `--env-file-if-exists=.env`,
а `migrate` и `generate` — встроенным в `drizzle-kit` dotenv. Добавлять флаг Node
к `migrate` не нужно, `drizzle-kit` читает `.env` сам.

`db:check-locking` проверяет то, чего не проверяют тесты: у PGlite одно соединение,
две транзакции в нём идут по очереди, и разойтись по строкам просто не могут.
Скрипт заводит собственную временную таблицу и удаляет её за собой — рабочие
очереди не трогает.

Пароль владельца не задаётся аргументом (остался бы в истории оболочки и в списке
процессов): `npm run owner` печатает ссылку `/invite/<токен>`, пароль ставится той же
формой, что и у клиентов.

Оболочка разработки — **Windows PowerShell 5.1**, в ней `&&` даёт синтаксическую ошибку.
Внутри npm-скрипта `&&` обрабатывает уже не PowerShell, поэтому `npm run check` работает
кроссплатформенно, а в консоли контрольная точка пишется как
`npm test; if ($?) { npm run typecheck }`.

Скрипта сборки нет: `outDir: "dist"` в `tsconfig` не задействован, код исполняется через tsx.
Отсюда состав зависимостей, который выглядит как ошибка, но ею не является:

- `tsx` лежит в `dependencies`, а не в `devDependencies`: на сервере им запускается
  `npm start`, и `npm ci --omit=dev` без него падает с `tsx: not found`.
- `drizzle-kit` остаётся dev-зависимостью намеренно: база облачная, `npm run migrate`
  катается с прод-строкой `DATABASE_URL` с любой машины — на сервере он не нужен.
- `--omit=optional` к установке добавлять **нельзя**: нативный бинарник argon2
  (`@node-rs/argon2-<платформа>`) объявлен опциональной зависимостью, и без него
  падает проверка пароля (S13) — уже в рантайме, а не при установке.
- PGlite (~30 МБ WASM) приезжает и в прод-установку. Это не наша dev-зависимость
  протекла: он опциональный peer `drizzle-orm`. Убирать нечем и не нужно.

Линтера и форматтера нет тоже: ни ESLint, ни Prettier в проекте не заведены, стиль
держится строгим `tsconfig` и ревью. Искать конфиг бесполезно — его нет.

`overrides` в `package.json` поднимает `esbuild` до 0.25 внутри `drizzle-kit`:
kit тянет заброшенный `@esbuild-kit/esm-loader` со старым esbuild, а своей версии
без него не выпустил. `npm audit fix --force` тут вреден — он откатывает drizzle-kit
до 0.18. После смены версии drizzle-kit проверять `npx drizzle-kit check`.

Node >= 20. Нативных модулей больше нет: `pg` — чистый JS, пересобирать после смены
версии Node нечего. PGlite тянет ~30 МБ WASM, но только в devDependencies.

Локальная проверка вебхука Instagram: туннель (`npx localtunnel --port 3000` или ngrok)
и URL в настройках приложения Meta.

## Архитектура

Процесс один: `src/server.ts` поднимает Fastify (кабинет, админка, вебхук) и в том же
процессе двумя `setInterval` крутит воркер (`WORKER_INTERVAL_MS`) и опрос TikTok
(`TIKTOK_POLL_INTERVAL_SEC`). Отдельного процесса воркера нет: `src/worker.ts` — это
две функции, `runIntake` (очередь → движок → outbox) и `runDelivery` (outbox → адаптер),
именно чтобы один шаг воркера вызывался из теста без таймеров и без сервера.
Оба таймера защищены флагом от наложения прогонов.

Четыре слоя, зависимости направлены только внутрь — к `core/`:

```
core/      types, scenario, matcher, engine, throttle   чистая логика, без сети и БД
storage/   schema, db, crypto, queries/, files, jsonMap   PostgreSQL через Drizzle
adapters/  instagram/ (push), tiktok/ (pull, фаза G)    платформенные детали
web/       session, html, csrf, http, forms, csv, routes/, views/  кабинет и админка
```

`web/` держит мелкие модули-механики и два каталога: `session.ts` (cookie → сессия →
`userId`), `html.ts` (разметка с экранированием), `csrf.ts`, `http.ts` (cookie, разбор
форм, заголовки), `forms.ts` (Zod-схемы форм конструктора), `password.ts` (argon2id
и dummy-хэш против тайминг-атаки, S13), `csv.ts`, `theme.ts` (выбор темы в cookie
и `safeBackPath` против открытого редиректа), `nav.ts` (роль, тема и путь возврата
одним объектом для шапки). Маршруты и представления разделены:
разметка меняется, когда меняется вид страницы, маршрут — когда меняется поведение.

`currentSession` — единственный вход к `userId`, и в нём две вещи, которые легко
«починить» обратно в лишние походы к облачной базе: сессия скользящая, но продлевается
записью не чаще раза в час (`REFRESH_AFTER_MS` — константа в `web/session.ts`,
не переменная окружения), а повторный вызов в том же запросе берёт результат
из `WeakMap` по объекту запроса — админка спрашивает сессию дважды
(хук роли и CSRF в обработчике). Граница этой памяти — один запрос, не больше:
`loadSession` соединяется с `users` и отсекает `disabled_at`, поэтому выход,
отключение клиента и разжалование роли действуют со следующего запроса (S12, S15).

Корень обслуживает двоих: без сессии `GET /` отдаёт лендинг (`views/landing.ts`),
с сессией — список воронок. Отдельного маршрута у лендинга нет не по небрежности:
Fastify не даёт зарегистрировать два обработчика одного пути, а человек, набравший
домен руками, должен попадать на витрину, а не на форму входа.

Витрина всегда светлая: `landingLayout` ставит `data-theme="light"` на `<html>`
жёстко. Цвета здесь часть оформления, а не настройка рабочего места;
переключатель темы остаётся в кабинете, где сидят часами.

Брендовая палитра (градиент Instagram) лежит в тех же токенах, что и остальное,
и подчиняется одному правилу: **градиент красит заливки, а не текст**. Белые буквы
читаются только на холодной половине (синий 5.4:1, фиолетовый 6.5:1, розовый 5.1:1),
на оранжевом и жёлтом контраст падает до 2.8:1. Поэтому кнопки, пузыри диалога
и градиентный текст заголовка держатся холодных цветов, а полный градиент из девяти
достаётся декору, где букв нет вовсе: полоса вверху, черта под заголовком, подсветка
холста пятнами, рамка последней плашки.

Витрина и кабинет — одна система оформления, а не две похожие. Держится это
на четырёх вещах, и ломается ровно там, где кто-то заведёт пятую:

- **главная кнопка одна** — `.btn--primary` с градиентом холодной половины
  палитры. Отдельной «фирменной» кнопки для лендинга нет намеренно: она
  разошлась бы с кабинетом на первой же правке;
- **акцент кабинета брендовый**: `--accent: #6246d6` в светлой теме (белый текст
  на нём 6.2:1), `#8a6dff` в тёмной, ссылки `--link` — `#6246d6` и `#c3b5ff`
  соответственно (5.8:1 и 9.8:1). Прежний синий `#1f5fd0` убран;
- **брендовая полоса** `.brandbar` стоит в `documentShell`, то есть появляется
  на каждой странице сервиса — кабинет, вход, приглашение, витрина;
- **радиусы общие**: `--radius: 14px`, `--radius-sm: 8px`, и карточки витрины
  берут токен, а не свои числа.

Первые три правила заперты тестами в `tests/web/style.test.ts`.

Файл стилей подключается с версией — `/app.css?v=<8 символов хэша содержимого>`
(`APP_CSS_VERSION` в `views/style.ts`). Без неё браузер держит стили столько,
сколько разрешил `cache-control`, и после выката показывает новую разметку по старым
правилам — то есть страницу вообще без вёрстки. Адрес с версией отдаётся с
`immutable` на год, голый `/app.css` — на пять минут, потому что сам он не обновится.

Тема оформления переключается формой, а не скриптом: CSP запрещает инлайновый JS,
а файла скриптов в проекте нет вовсе. `POST /theme` пишет cookie и возвращает
на исходный путь, `layout` ставит `data-theme` на `<html>`. Значений три:
«system» — отсутствие выбора, при нём решает `prefers-color-scheme`. Тёмные токены
в `views/style.ts` написаны один раз и подставляются в обе ветки CSS — под
медиазапрос и под явный выбор.

`files` — модуль внутри `storage/`, а не отдельный слой: он хранит и отдаёт байты.
Байты лежат в `FILES_DIR` (по умолчанию `./data/files`), разложенные по подкаталогам
`<user_id>/`. `data/` в `.gitignore`: в свежем чек-ауте каталога нет, его создаёт
сам код при первой загрузке.
`jsonMap.ts` — там же: он разбирает `context_json` обратно в `Map` и держит правило
«контекст диалога не объектный литерал» в одном месте (S6).

Универсальность держится на двух типах из `core/types.ts`: всё входящее приводится
к `IncomingEvent`, всё исходящее — к `OutgoingAction`. Ядро не знает, откуда пришло
событие и куда уйдёт ответ; `DeliveryContext` описывает адресацию.

`ReplyThrottle` из `core/throttle.ts` создаётся трижды с разным смыслом: троттлинг
ответов бота (S8), троттлинг на клиента (S20) и троттлинг попыток входа (S22). Класс
общий, окна и цена ошибки — разные; не путать экземпляры при чтении `server.ts`.

Движок — чистая функция `step(scenarios, state, event) -> { state, actions }`:
ни `await`, ни БД, ни сети. Вся бизнес-логика тестируется без интернета и без моков.

Конструктор в браузере сохраняет строки в `automations` и `automation_steps`; перед
исполнением `buildScenario` собирает из них `Scenario` — тот же тип, что раньше приходил
из YAML. Поэтому `engine.ts`, `matcher.ts`, `throttle.ts` при смене продукта не менялись.
YAML-путь (`parseScenario` / `loadScenarios`, каталог `scenarios/`, зависимость
`js-yaml`) удалён вместе с требованием S5: воронки идут из БД, и разбирать чужой
YAML сервису больше негде. Вместе с ним из `core/` ушли `node:fs` и `node:path` —
запрет на `node:` в ядре проверяет `tests/core/purity.test.ts`.

Разницу push/pull скрывает адаптер, а не ядро: у Instagram есть webhook, у TikTok
webhook на комментарии не существует — только polling, и DM API у TikTok нет вовсе.
Отсюда три узких интерфейса в `src/adapters/types.ts`: `MessageSender`,
`WebhookSource extends MessageSender` (+`parseWebhook`),
`PollingSource extends MessageSender` (+`poll`).

Поток данных (HTTP-обработчик обязан ответить быстро — Meta отключает медленные приложения):

```
Instagram: Meta -> POST /webhooks/instagram -> подпись (S1) -> владелец аккаунта (S17)
                -> event_queue -> 200 OK
worker:    event_queue -> воронки этого клиента -> состояние диалога -> step()
                -> сохранение состояния -> outbox -> adapter.execute() -> leads
web:       браузер -> сессия -> userId -> запросы только с этим userId
```

Надёжность лежит в БД, не в Redis: `processed_events` (UNIQUE по `dedupe_key`, обе
платформы доставляют at-least-once), `event_queue`, `outbox` с `attempts` /
`next_attempt_at` (экспоненциальная задержка). Осмысленный 4xx от платформы — не
повторять, пометить, показать клиенту. Выход за 24-часовое окно Instagram — не сетевая
ошибка, а бизнес-ситуация: решает сценарий.

Строки очередей не читаются, а **забираются** — так две копии процесса не сделают
одну работу дважды. Способа два, и они разные не по вкусу, а по наличию сети внутри:

- `takePendingEvents` + `runIntake`: `FOR UPDATE SKIP LOCKED` внутри транзакции на
  всю пачку. Внутри только БД, транзакция коротка, блокировка держится до конца.
- `takeDueOutbox` + `runDelivery`: короткая транзакция забирает строки и двигает
  `next_attempt_at` на `OUTBOX_LEASE_SEC` вперёд (лизинг), сеть идёт уже вне
  транзакции. Транзакция вокруг доставки при откате отправила бы человеку то же
  сообщение второй раз, а блокировки висели бы всё время ответа платформы.
  Упавший процесс возвращает строку в работу сам — по истечении лизинга.

### Карта маршрутов

Какой URL лежит в каком файле — иначе искать приходится грепом:

```
GET  /webhooks/instagram        routes/webhooks.ts     хендшейк (S2)
POST /webhooks/instagram        routes/webhooks.ts     подпись сырых байт (S1)
GET  /login   POST /login       routes/auth.ts         троттлинг входа (S22)
POST /logout                    routes/auth.ts
GET  /                          routes/dashboard.ts    гостю лендинг, клиенту воронки
POST /automations/:id/toggle    routes/dashboard.ts    включить/выключить
GET  /automations/new           routes/constructor.ts
POST /automations               routes/constructor.ts
GET  /automations/:id           routes/constructor.ts
POST /automations/:id           routes/constructor.ts
GET  /leads                     routes/leads.ts

POST /files/:id/delete          routes/files.ts

POST /invite/:token             routes/invite.ts       установка пароля
```

Админка — отдельный плагин Fastify с префиксом `/admin` и хуком `onRequest`
на роль: проверка стоит один раз на входе в плагин, а не копируется в каждый
маршрут (`registerAdminRoutes` в `src/web/routes/admin.ts`). Отдельного маршрута
на скачивание файла клиентом нет: байты уходят наружу только адаптером, в директ.

### Таблицы

Двенадцать таблиц, и всё висит на `users` каскадом — удаление клиента уносит
его данные без отдельного кода:

```
users               клиенты и владелец сервиса, роль, disabled_at
platform_accounts   подключённые аккаунты, токен шифрованный (S4)
automations         воронки; automation_steps — их шаги (висят на automation_id)
files               метаданные вложений; байты — в FILES_DIR
leads               заявки; conversations — состояние диалога, context_json
event_queue         входящие события; processed_events — дедупликация
outbox              исходящие, attempts / next_attempt_at
sessions            сессии кабинета; invites — приглашения по ссылке
```

`user_id` есть у каждой, кроме `users` и `automation_steps` (шаг принадлежит
воронке, а воронка — клиенту). Тот же список перечислен в `TRUNCATE` внутри
`tests/storage/helpers.ts`: новая таблица без ссылки на клиента молча копила бы
строки между тестами, и падение всплыло бы в чужом тесте.

### Три неочевидных места в старте

**Парсер `application/json` в приложении глобальный и отдаёт `Buffer`.**
`registerWebhookRoutes` подменяет его ради S1 — подпись считается от сырых байт,
и разобранное Fastify тело для этого не годится (`src/web/routes/webhooks.ts`).
Подмена действует на весь экземпляр, а не на один маршрут. Отсюда два следствия:
второй `addContentTypeParser` на тот же тип уронит старт, а новый JSON-маршрут
получит буфер, а не объект. Кабинету это безразлично — он работает на формах.

**`void warmUp(3)` в `server.ts`.** Пул открывает три соединения заранее и не
блокирует `listen`. База облачная, рукопожатие TLS стоит секунды, страница кабинета
шлёт несколько запросов разом — без прогрева за них платит первый зашедший.
Ошибка прогрева намеренно не роняет сервер: не прогрелись — просто медленнее.
Там же `idleTimeoutMillis: 0` и `keepAlive: true`: соединение из пула не закрывается
по простою, иначе следующий клик снова оплачивает рукопожатие.

**Логгер Fastify усечён по пути.** Fastify пишет URL каждого запроса, а в
`/invite/<токен>` лежит секрет: сериализатор `req` в `server.ts` подменяет такой путь
на `/invite/:token` (S9). Само это не произойдёт — новый маршрут с секретом в пути
придётся добавить туда же.

## Обязательные правила

Нарушение любого из них — дефект, даже если тесты зелёные.

- **`src/core/` не содержит слов** `instagram`, `tiktok`, `meta`, `fastify`, `drizzle`,
  `fetch(`, `process.env`, `import(`. Единственное исключение — union `Platform`
  в `core/types.ts`. Проверяет `tests/core/purity.test.ts`.
- **Никаких `any`, `as unknown as`, `!` (non-null assertion)** в `src/`. В тестах
  `as unknown as NodeJS.ProcessEnv` допустим — им подделывают окружение.
  `tsconfig` строгий, включая `noUncheckedIndexedAccess`.
- **`process.env` читается только в `src/config.ts`.** Остальной код получает `Config`
  параметром. Ошибка валидации env печатает только имена переменных, не значения (S10).
  Ключи остаются в `SCREAMING_SNAKE`: `cfg.PORT`, не `cfg.port`. Новая переменная —
  три синхронные правки: `EnvSchema`, `.env.example`, тест в `tests/config.test.ts`.
  Значение по умолчанию есть почти у всех; без него — шесть обязательных:
  `DATABASE_URL`, `META_APP_SECRET`, `META_VERIFY_TOKEN`, `CREDENTIALS_ENC_KEY`,
  `SESSION_SECRET`, `PUBLIC_BASE_URL`. Без любой из них процесс не стартует.
  Два осознанных исключения, оба вне `src/` и оба не «недоделка»: `drizzle.config.ts`
  (инструмент сборки, в `tsconfig.include` не входит, в рантайм приложения не попадает)
  и `scripts/check-tiktok.ts` (`TIKTOK_TEST_TOKEN` — токен для ручной проверки живого
  API; в `EnvSchema` его нет намеренно, приложению он не нужен, и правило трёх правок
  на него не распространяется).
- **`DATABASE_URL` — секрет.** Это строка подключения с паролем, а не путь к файлу:
  обязательна, без значения по умолчанию, префикс (`postgres://`, `postgresql://`)
  проверяется при старте, TLS задаётся в самой строке.
  В сообщении об ошибке — только имя переменной (S10).
  Рабочий режим — `sslmode=verify-full&sslrootcert=./certs/supabase-prod-ca-2021.crt`:
  шифрование плюс проверка подлинности сервера. Сертификат провайдера закоммичен
  в репозиторий (`certs/supabase-prod-ca-2021.crt`), а путь в строке относительный —
  поэтому любая команда запускается из корня проекта, иначе TLS не поднимется.
  Один `sslmode=require` в этой версии `pg` значит то же самое, что `verify-full`,
  и без корневого сертификата провайдера
  падает с `self-signed certificate in certificate chain`. Понижать до `no-verify`
  нельзя: пароль базы и токены клиентов уедут любому, кто встанет посередине.
- **Объект ошибки драйвера не логируется целиком** — никогда, даже в отладке.
  У `pg` внутри лежат текст запроса и его параметры, то есть тело сообщения клиента
  или зашифрованный токен (S4, S9). Проверяет `tests/security/logging.test.ts`.
- **Владелец — первый аргумент.** Каждая функция в `src/storage/queries/`, читающая
  или меняющая данные клиента, принимает `userId` первым параметром, и владелец входит
  в условие выборки (`WHERE id = ? AND user_id = ?`), а не проверяется отдельным `if`
  после неё (S11). Шесть осознанных исключений, все задокументированы в коде:
  `resolveAccountOwner` (определяет владельца по вебхуку), `takePendingEvents` и
  `takeDueOutbox` (воркер разгребает очереди всех клиентов, `userId` уже лежит
  в строке), `listClients` (владельцу сервиса принадлежат все клиенты, защищает её
  хук роли плагина `/admin`, а не `WHERE`), `consumeInvite` и `peekInvite` (гость ещё
  не аутентифицирован — владелец здесь определяется, как в `resolveAccountOwner`)
  и `listActivePlatformAccounts` (поллер TikTok обходит аккаунты всех клиентов,
  как воркер — очереди; `userId` уже лежит в строке аккаунта).
  Общее у них одно: во всех этих случаях пользователя ещё или вообще нет — воркер,
  вебхук, гость по ссылке, — либо роль владельца делает вопрос «чей это объект»
  бессмысленным.
- **`user_id`, роль и любые признаки владения никогда не читаются из тела запроса** (S14).
  Владелец берётся только из сессии. Zod-схема формы описывает ровно разрешённые поля.
- **ESM.** `"type": "module"`, относительные импорты пишутся с расширением `.js`,
  даже когда файл `.ts`. Компилятор это не проверяет (`moduleResolution: "bundler"`),
  vitest и tsx прощают — падает только Node. Проверяет `tests/esm-imports.test.ts`.
- **Разметка собирается только тегом `html`** из `src/web/html.ts`. Конкатенация строк
  с данными пользователя запрещена: тег экранирует подстановку по умолчанию, а сырой
  HTML требует явного `raw()` — его видно в месте вызова (S21).
- **Имена полей в формах со списками нумеруются** (`say_0`, `say_1`), а не повторяются.
  Разборщик форм построен на `Object.fromEntries(new URLSearchParams(...))` и от
  одинаковых имён оставляет только последнее значение — повторяющиеся имена молча
  потеряли бы все элементы, кроме последнего.
- **Контекст диалога — `Map<string, string>`,** не объектный литерал: ключи приходят
  от пользователя, литерал даёт prototype pollution через `__proto__` (S6).
  В БД сериализуется в `context_json`.
- **Регулярные выражения в триггерах запрещены** (ReDoS, S7): только `exact`,
  `contains`, `starts_with`. Текст пользователя обрезается по длине до матчинга.
- **Секреты и ПД не логируются** выше уровня `debug` — токены, тела сообщений,
  телефоны, в том числе через «залогировать весь объект ошибки» (S4, S9).
- **Тест пишется до реализации, каждая задача заканчивается коммитом.**
  Сообщения коммитов и комментарии в коде — на русском.

## Требования безопасности

Полный список — раздел 7 спеки. Тесты помечаются номером `S…` в названии
(`it('S11: клиент не видит чужие аккаунты...')`). Самое важное:

- **S1 (CRITICAL).** `X-Hub-Signature-256` — HMAC-SHA256 от **сырых байт** тела на App
  Secret, сравнение только `timingSafeEqual` с предварительной проверкой длины,
  несовпадение → `403` без тела. Fastify парсит JSON по умолчанию, поэтому raw body
  нужно сохранить до парсинга: `JSON.stringify(req.body)` ≠ исходным байтам.
- **S2 (CRITICAL).** `hub.verify_token` в GET-хендшейке сравнивается constant-time.
- **S11 (CRITICAL). IDOR.** Клиент не достаёт чужие воронки, файлы, заявки, диалоги
  и аккаунты ни чтением, ни изменением, ни удалением.
- **S12 (CRITICAL). Function-level авторизация.** Маршруты админки доступны только роли
  `owner`, проверка на сервере на каждом маршруте. Это **другая** проверка, чем S11:
  там «твой ли объект», тут «твоя ли роль».
- **S13 (CRITICAL). Пароли** — только хэш (argon2id, иначе bcrypt cost ≥ 12). Ответ при
  неверном логине и при неверном пароле одинаков.
- **S3, S4, S6, S7, S8** — эхо-петля, шифрование токенов AES-256-GCM, `Map` вместо
  литерала, запрет regex, троттлинг. S5 (безопасный YAML) снят вместе с YAML-путём:
  разбора YAML в сервисе больше нет.
- **S14–S22** — mass assignment, сессии и CSRF, загрузка файлов (сигнатура, а не только
  MIME), изоляция вебхуков, path traversal, троттлинг входа и на клиента, XSS,
  заголовки безопасности.


## Тесты

`tests/` зеркалит `src/`. Пять уровней: **unit** (движок и матчер — таблица
«событие → ожидаемые действия», без моков), **contract** (адаптеры против сохранённых
реальных тел вебхуков в `fixtures/`), **security** (S1, S2, S3 и S11–S22 отдельными
тестами), **integration** (`tests/worker.test.ts` — фейковый адаптер + PGlite, прогон воронки
целиком; отдельного каталога у этого уровня нет),
**web** (маршруты через `fastify.inject()`, без реального HTTP).

«security» — уровень, а не каталог: в `tests/security/` лежит один `logging.test.ts`,
остальные S-тесты стоят рядом с кодом, который проверяют (`tests/web/admin.test.ts`,
`tests/storage/queries/`, `tests/adapters/instagram/signature.test.ts`). Искать их
по номеру требования: `npx vitest run -t "S11"`.

Обязательный тест в каждой задаче, трогающей данные: **два клиента в одной базе** —
клиент A не достаёт ничего из данных клиента B.

База для теста берётся из `tests/storage/helpers.ts`: `await createTestDb()` даёт
пустую базу с применёнными миграциями. Новый тест с БД начинается с неё, а не со своего
`openDb` — тесты не ходят в облако и не требуют секретов.

Под ней PGlite — настоящий Postgres, собранный в WASM. Отсюда три следствия:

- функция асинхронная, и запуск базы стоит около секунды, поэтому база **одна на файл**
  тестов, а между тестами таблицы чистятся `TRUNCATE`. Оттуда же поднятый таймаут
  в `vitest.config.ts`;
- у PGlite одно соединение: две транзакции выполняются по очереди, и поведение
  `SKIP LOCKED` в тестах непроверяемо. Тесты (`tests/storage/locking.test.ts`)
  проверяют текст запроса и лизинг, живую гонку — `npm run db:check-locking`;
- `.all()` и `.run()` больше не существуют: запрос drizzle сам является промисом,
  и без `await` он просто не выполняется.

Часть правил из этого файла не на совести ревью, а заперта тестом. Ломается
правило — падает конкретный файл:

| правило | тест |
|---|---|
| `core/` без платформ, без `node:` и `process.env` | `tests/core/purity.test.ts` |
| относительные импорты с расширением `.js` | `tests/esm-imports.test.ts` |
| объект ошибки `pg` не логируется целиком | `tests/security/logging.test.ts` |
| `FOR UPDATE SKIP LOCKED` и лизинг outbox | `tests/storage/locking.test.ts` |
| два клиента в одной базе не видят друг друга | `tests/web/isolation.test.ts` |
| значения по умолчанию и S10 в ошибке конфигурации | `tests/config.test.ts` |

## Открытое решение владельца

`core/matcher.ts` — функция `matches(trigger, userText)` реализована владельцем и
остаётся его зоной ответственности: от строгости сравнения зависит доля клиентов,
которых бот проигнорирует. Компромиссы — регистр (кириллица требует
`toLocaleLowerCase`), ложные срабатывания `contains` («цена меня не волнует» → бот шлёт
прайс на претензию), мусор вокруг («цена?», « цена », «цена 🙏»). В SaaS-версии цена
ошибки выше: правило действует сразу для всех клиентов сервиса.
